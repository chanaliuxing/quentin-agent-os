# Project Quentin – Meta-Agent v3 架构总览

> 一个可自进化的通用智能体操作系统  
> **特点：**多领域、多模型、自观察、自改进、可回滚、可做学术实验

---

## 0. 目标与非目标

### 0.1 目标

- 提供一个 **通用的、自进化的智能体骨架**：
  - 不绑定任何具体业务领域（Desktop / Legal / Trading 都只是适配层）。
  - 不绑定具体模型供应商（接任何 OpenAI / DeepSeek / 本地模型）。
- 支持四大能力：
  1. 任务规划与执行（Cognitive Loop）
  2. 多层记忆（Memory Fabric）
  3. 自我防御与异常止损（Immune Loop）
  4. 自编程与自我演化（Self-Programming + Research Layer）

### 0.2 非目标

- 不追求“完全无人类监督”的自治 AI。
- 不允许 AI 修改：
  - 安全内核（Safety Kernel）
  - 数据 Schema（Memory / Trace / Patch）
  - 高风险域里的核心风控逻辑。
- 不试图一次性解决所有研究问题：
  - 多智能体复杂博弈
  - 完全自动架构重构
  - 全局最优策略

## 1. 四层智能结构（Logic Layers）

```text
L3  Research & Evolution Layer      # 研究与演化策略层
L2  Meta Layer                      # 评估 & 自改层
L1  Base Layer                      # 执行层
L0  Infra & Kernel Layer            # 基础设施 & 安全内核
1.1 L0 – Infra & Kernel Layer
**职责：**安全、存储、运行环境。

模块：

quentin/kernel/safety.py – SafetyKernel

权限、限流、自编程开关、降级模式

quentin/infra/storage/kv_store.py – KVStore

抽象出来的键值存储（本地 JSON / Redis / etc.）

quentin/infra/logging.py – Tracer

结构化 Trace / 日志 / span 记录

运行环境：

本地进程 / 容器 / K8s（由外部 DevOps 决定）

约束：AI 不允许修改 L0 层的任何代码和 Schema。

1.2 L1 – Base Layer（执行层）
**职责：**接任务、拆任务、调用模型和工具、读写记忆。

核心组件：

quentin/runtime/agent_runtime.py – AgentRuntime

聚合整个系统的依赖：Memory、Router、Loops、Self-Programming 等。

quentin/cognitive/loop.py – CognitiveLoop（假定存在）

任务执行闭环：Planner → Executor → Critic → Trace & Memory。

quentin/memory/fabric.py – Memory Fabric

STS / MTS / LTS 三层记忆系统（见下文）。

quentin/routing/model_router.py – ModelRouter

对接底层 LLM 客户端，记录调用日志。

quentin/tools/manager.py – ToolManager（假定存在）

工具 & 技能的生命周期与注册。

quentin/multi_agent/coordinator.py – MultiAgentCoordinator

Speed / Safety / Cost / Domain-Expert 多智能体模型路由策略。

1.3 L2 – Meta Layer（评估 & 自改层）
**职责：**评测、对比、触发自改，处理异常案例。

核心组件：

quentin/eval/harness.py – EvalHarness

统一的“评测一个策略 / 变体”的入口（可替换为学术算法）。

quentin/experiments/orchestrator.py – ExperimentOrchestrator

create_experiment / run_experiment / compare_variants / export_results。

quentin/experiments/registry.py – VariantRegistry

变体（策略/模型/路由器）注册表。

监控 error / cost / latency，生成 ImmuneCase。

quentin/meta/self_improvement.py – SelfImprovementManager

负责把 ImmuneCase → Patch → Experiment 串起来。

1.4 L3 – Research & Evolution Layer
**职责：**系统级研究与演化策略：

决策“改哪里、怎么改、投多少算力”。

管理实验、分析 patch 收益、分配资源。

核心组件：

quentin/experiments/orchestrator.py – 实验管理（也是 Research 的入口）。

quentin/self_programming/engine.py – SelfProgrammingEngine

生成/管理 PatchRecord，跑测试/回滚。

各种研究接口：

docs/RESEARCH_API.md

HTTP API（/experiments/...）+ CLI (qctl exp-*, qctl patch-*)

2. Memory Fabric：多层记忆系统
目录：quentin/memory/

记忆按“时间尺度”和“稳定性”分层：

STS – Short-Term Store

会话级 / 任务级，存放当前任务的上下文、临时总结。

MTS – Mid-Term Store

项目级 / 版本级，存放某段时间内重复使用的知识 / 模式。

LTS – Long-Term Store

跨项目 / 跨版本的稳定知识。

每条 Memory 的 schema（简化）：

{
  "id": "mem_xxx",
  "kind": "episodic | semantic | procedural",
  "tier": "STS | MTS | LTS",
  "content": "...",
  "vector": [ ... ],
  "relations": { "related_to": ["..."], "domain": "..." },
  "update_policy": {
    "promotion_rule": "...",
    "decay_rule": "...",
    "consolidation_batch": "nightly | weekly | manual"
  }
}
迁移规则：

新记忆 → 先进入 STS。

被 Sleep Loop 多次引用/证明有用 → 升到 MTS。

跨任务/跨域稳定复用 → 升到 LTS。

STS 定期清理；MTS 可压缩；LTS 仅通过 supersedes 替换。

3. 四个闭环（Loops）
3.1 认知循环（Cognitive Loop）
文件：quentin/cognitive/loop.py（架构约定）

流程：

接任务（task）

检索 Memory（STS/MTS/LTS）做上下文增强

Planner 规划步骤

Executor 调用工具 / 模型

Critic 评估结果，必要时重试或调整

写 Trace & Memory（execution_summary / lessons_learned）

要求：

每一步必须写 Trace（否则视为未执行）。

结束后写入：

execution_summary（结构化）

lessons_learned（可选）

3.2 免疫循环（Immune Loop）
文件：quentin/immune/loop.py（架构约定）

职责：

监控系统指标：

error rate / latency / cost / reward

检测异常并触发：

降级（关闭部分自编程、减少探索）

回滚到稳定版本

生成 ImmuneCase 供 Research Layer 分析

ImmuneCase 典型字段（简化）：

{
  "case_id": "immune_xxx",
  "status": "open | investigating | closed",
  "window_start": "...",
  "window_end": "...",
  "metrics": { "error_rate": 0.5, "latency": 2.3 },
  "suspected_modules": ["planner.v1", "skill.extract_xxx"],
  "traces": ["trace_id_1", "trace_id_2"]
}
3.3 睡眠循环（Sleep / Consolidation Loop）
文件：quentin/sleep/loop.py（架构约定）

职责：

周期性运行（夜间 / 每周）：

从 Trace 中抽取新的 Semantic Memory / Procedural Skills。

迁移 Memory（STS → MTS → LTS）。

收集训练/对齐数据对（失败→成功，坏计划→好计划）。

控制资源预算：一次运行处理多少 Trace / 消耗多少 Token。

3.4 技能与代码进化循环（Skill & Code Evolution）
关键组件：

quentin/skills/miner.py（假定存在）

从成功 Trace 中挖掘可抽象的技能。

quentin/self_programming/engine.py

生成并测试 patch（代码级更新）。

quentin/meta/self_improvement.py

把 ImmuneCase → Patch → Experiment 串起来。

流程示意：

ImmuneLoop / SleepLoop 标记问题或机会
 → SelfImprovementManager 建议 Hotspots
   → 创建 PatchRecord（手动 or LLM 生成）
      → SelfProgrammingEngine 跑测试
         → ExperimentOrchestrator 建实验对比
            → 结果写回 PatchEvalSummary / Metrics
               → 人类 Gate 或自动应用（低风险域）

## 1. 实验系统（Experiments）

### 1.1 数据模型

文件：`quentin/experiments/schemas.py`

- `ExperimentConfig` – 创建实验的配置：
  - `name / description`
  - `eval_kind` – `"offline" | "online" | "custom"`
  - `dataset` – 任意字符串标识（如 `"desktop_dev_small"`)
  - `variants: List[VariantConfig]`

- `VariantConfig`：
  - `variant_id` – 唯一 ID
  - `kind` – 如 `"model_router" | "planner" | "patch_toggle"`
  - `params` – 任意参数字典（由具体模块解释）

- `ExperimentRecord`：
  - 持久化的实验记录：= config + `status` + `runs`

- `ExperimentRunResult`：
  - 一次运行的结果：`metrics / status / error / meta`

### 1.2 Orchestrator API（Python）

文件：`quentin/experiments/orchestrator.py`

```python
from quentin.experiments.orchestrator import ExperimentOrchestrator
from quentin.experiments.schemas import ExperimentConfig, VariantConfig

orch: ExperimentOrchestrator = ...

cfg = ExperimentConfig(
    name="my_new_algo_vs_baseline",
    eval_kind="offline",
    dataset="my_dataset_v1",
    variants=[
        VariantConfig(
            variant_id="baseline",
            kind="planner",
            params={"impl": "planner_v1"},
        ),
        VariantConfig(
            variant_id="my_algo",
            kind="planner",
            params={"impl": "planner_meta_rl"},
        ),
    ],
)

exp = await orch.create_experiment(cfg)
exp = await orch.run_experiment(exp.experiment_id)
compare = await orch.compare_variants(exp.experiment_id, metric="score")
results = await orch.export_results(exp.experiment_id)

2. 评测框架（EvalHarness）
文件：quentin/eval/harness.py

默认实现是一个 占位版，只返回：

metrics = {
  "score": 0.0,
  "notes": "EvalHarness v1 placeholder",
  ...

2.1 如何替换为你的评测逻辑？
直接修改 EvalHarness.run_variant：

class EvalHarness:
    async def run_variant(self, exp: ExperimentRecord, variant: VariantConfig) -> ExperimentRunResult:
        # 1. 根据 exp.eval_kind / dataset 选择评测策略
        # 2. 把 variant.params 传给你的算法
        # 3. 返回 metrics = {"score": ..., "other_metric": ...}

        metrics = await my_eval_algo(exp, variant)

        run = ExperimentRunResult(
            run_id=...,
            experiment_id=exp.experiment_id,
            variant_id=variant.variant_id,
            status=ExperimentRunStatus.succeeded,
            metrics=metrics,
            ...
        )
        return run
建议：

metric="score" 尽量统一为 “越大越好” 的指标；

如果是多指标，可以用 metrics = {"score": 综合分, "acc": x, "latency": y}；

所有评测过程建议写 Trace，便于调试和研究。

8. 如何接入你的论文 / 算法？
8.1 替换 Planner / Critic
定义一个新 Planner 实现，挂在 CognitiveLoop 中。

在 ExperimentConfig 里，将不同 Planner 作为 variants，对比表现。

8.2 新的模型路由算法
在 MultiAgentCoordinator 中增加一个新“角色”或替换聚合逻辑。

用 ModelUsageRecord 做训练数据，训练 bandit / policy network。

用 ExperimentOrchestrator 对比不同路由策略。

8.3 新的自编程方法
在 SelfProgrammingEngine 外面加一层：

根据 Trace / ImmuneCase / Metrics，用 LLM / 代码生成器自动构建 PatchRecord。

使用现有的测试 / 回滚 / 实验框架，避免破坏系统。

9. 安全与边界
Self-Programming 只能触碰 allowed_roots 下的文件：

默认是 ["mutable", "quentin/skills"]。

安全内核（SafetyKernel）不可被修改：

仅通过公开方法读取 / 调整状态。

高风险域（如 Trading / Legal）：

推荐在业务 Adapter 层再加一层白名单、风险控制和人工 Gate。

本文件的目的，是让你在 不破坏整体架构 的前提下，
可以方便地把你的研究成果（算法 / 策略 / 模型）挂进这个通用智能体系统。

你可以把它当成一个「研究版操作系统」，
需要什么模块，就在对应的“挂载点”里写你的代码。
